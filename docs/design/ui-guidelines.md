## 1. 調査のまとめ（2026 年時点）

| 傾向 | 内容 | このアプリでの扱い |
| --- | --- | --- |
| 静かな画面（calm interface） | 装飾を減らし、判断の数を減らし、余白と階層で読ませる。ナビゲーションは目的地に着いたら一段引き、コンテンツを主役にする | 採用（原則 1） |
| アイコンを減らし、小さくする | 情報量の多い製品でも、アイコンの数・大きさ・色付きの背景を減らしてノイズを下げている | 採用（§3） |
| 動きは説明のために使う | 進行中であること・状態の変化を伝える動きだけを残す。装飾の動きは減らす | 採用（§6） |
| AI の働きを見せる | 最初の反応をすぐ返し、ストリーミングし、失敗と再試行の道を用意する。なぜその提案なのかを見せる | 採用（原則 3・§7） |
| アクセシビリティを基盤として扱う | コントラスト・キーボード操作・動きを減らす設定を最初から組み込む | 採用（§5） |
| 入力手段の行き来 | タッチ・声・キーボードを意識せずに切り替えられる | 採用（声で話す機能がある） |
| トークンによるデザインシステム | 色・余白・動きを変数で管理する | 導入済み（ADR-009） |
| 透明・ガラスの質感 | 半透明の操作部品は、背景によってコントラストと読みやすさが落ちるという批判がある | **採用しない**（§8） |
| 3D・空間的な UI | AR・空間コンピューティング向けの表現 | 対象外 |

傾向は「見た目の流行」より「認知負荷を下げる」「状態を正直に見せる」方向にそろっている。このドキュメントの規則もこの 2 つから導く。

## 2. 原則

主な利用端末は PC（マウスとキーボード）。タッチ端末でも操作は完了できることを前提にする。

1. **主役は対話とノート**。ナビゲーション・装飾・補助情報は一段引く。1 画面で強調（`brand` の塗り・影・動き）を使うのは 1〜2 か所に絞る。
2. **学ぶ人に考えさせ、操作には考えさせない**。プロテジェ効果を得るには、頭を使う対象が学習内容であるべきで、UI の解読に頭を使わせない。迷わせるくらいならラベルを出す。
3. **AI が何をしているかを正直に見せる**。待ち・生成中・失敗を隠さない。ただし、AI がこれから問う内容は先に見せない（既存の決定。CLAUDE.md の「学習中の進捗表示」）。
4. **どの入力でも同じことができる**。マウスのホバーでしか見えないもの・できないことを作らない（キーボード・タッチ・声）。
5. **一度決めた形を繰り返す**。同じ種類の操作は、どの画面でも同じ位置・同じアイコン・同じ文言にする。

## 3. アイコンとラベル

### 3.1 結論

「アイコンを使うと明示的で分かりやすい。ただしアイコンだけでは分からないことが多いので、ホバーで説明を出す」という考えは**半分正しい**。

- **正しい点**: アイコンは見つけやすく、何度も使う操作を素早くする。アイコンだけのボタンにツールチップを付けるのは、主要なデザインシステムが共通して推奨している形。
- **足りない点**: 調査では、意味が普遍的なアイコンはごく少ない（家・印刷・検索の虫眼鏡など）。そのため、**主要な操作のラベルは常に見せる**のが推奨で、ホバーでラベルを出すのは次善の策とされている。理由は 3 つ。
  1. ホバーはタッチ端末に存在しない（スマホ・タブレットではツールチップが出ない）
  2. 気づかれない。カーソルを乗せるまで、そこに説明があると分からない
  3. 操作のたびに乗せて待つ手間がかかる
- **2026 年の傾向**: 情報量の多い製品ほど、アイコンを減らして小さくし、文字と余白で整理する方向にある。アイコンを増やすほど明示的になるわけではない。

アイコンを使うかではなく、**ラベルを常に見せるか・ツールチップに任せるかを、操作の種類で決める**。

### 3.2 判断表

| 操作の種類 | 形 | 例 |
| --- | --- | --- |
| 画面の主要な操作（その画面に来た目的） | アイコン＋常に見えるラベル、またはラベルだけ | 「学習を始める」「ノートを作成」「声で話す」 |
| ナビゲーション | アイコン＋ラベル。狭くて隠すときだけツールチップ | サイドバーのリンク（折りたたみ時はツールチップ） |
| 意味が普遍的で、繰り返し使う補助操作 | アイコンだけ＋ツールチップ＋`aria-label` | 閉じる（×）・コピー・送信・再生 ▶・前後の移動 |
| 意味が曖昧なアプリ固有の操作 | アイコン＋ラベル。ツールチップだけに頼らない | 観点マップ・まとめノートに入れる |
| 取り消せない・破壊的な操作 | ラベル必須。確認は `AlertDialog` | 削除 |
| 状態の表示（操作でないもの） | アイコンにテキストを添える。色だけで区別しない | 観点のカバー状況・緊急度 |

迷ったらラベルを出す。ラベルを出す余白が無いときに、初めてツールチップを検討する。

### 3.3 ツールチップの規則

- **共通部品の `Tooltip`（`components/ui/tooltip.tsx`）を使う**。`title` 属性は使わない（ESLint が error にする。キーボードのフォーカスで出ない・タッチで出ない・出るまでが遅い・見た目を揃えられない）。
- **ホバーとキーボードのフォーカスの両方で出す**。Esc で閉じられ、ポインタを乗せても消えないこと（WCAG 1.4.13。Radix の既定で満たす）。
- **文言は 1〜数語の動詞句**で、何が起きるかを書く。アイコンの名前を書かない（×「鉛筆」→ ○「編集して再送信」）。
- **キーボードショートカットがある操作は、ツールチップに併記する**（ショートカットを自然に覚えてもらえる）。
- **作業を終えるのに必要な情報をツールチップに入れない**。必要な情報は画面に常に出す。
- **主な利用端末は PC だが、タッチ端末では出ない前提で設計する**。ツールチップが出なくても操作は完了できること。説明がないと使えない操作なら、ラベルを常に出すか、クリックで開く `Popover` にする。
- **アイコンだけのボタンには必ず `aria-label`** を付ける（ツールチップの文言と同じでよい）。ボタンを `Tooltip` で包むには `TooltipLabel`（`components/ui/tooltip.tsx`）を使う。
- 出るまでの遅延は `TooltipProvider` の既定値（400ms。続けて別のツールチップに乗せたときは遅延なし）に任せ、部品ごとに `delayDuration` を変えない。

### 3.4 アイコン

- `lucide-react` だけを使う。同じ意味には同じアイコンを使い、別の意味に同じアイコンを使わない。
- 大きさは `size-4` を基本にし、本文と並べる小さな表示は `size-3.5`。
- アイコンに色付きの背景を敷かない。色は意味（`tone`）を持つときだけ付ける。

## 4. 状態の網羅

UI を作ったら、次の状態をすべて見本ページ（`app/<名前>-preview/`）で確認する。

| 状態 | 規則 |
| --- | --- |
| 読み込み中 | 中身の形が決まっているなら `Skeleton`、決まっていないなら `Spinner`。全画面は `LoadingOverlay`。サーバーで取得する画面（`notes` / `collections`）は `loading.tsx` に `Skeleton` を置く |
| 空 | `EmptyState`。次に何をすればよいかを 1 つ示す |
| エラー | 何が起きたかと、次にできること（再試行など）を書く。入力を消さない |
| 一部だけある | 欠けた項目を詰めて表示する。空欄やプレースホルダーを並べない |
| 長いテキスト | 折り返しと `line-clamp` の両方を確認する。省略したら全文を読める手段を用意する |
| 狭い幅 | 幅 375px でレイアウトが崩れず、横スクロールが出ないこと |
| ダーク | ライトと同じ情報が読めること |
| キーボード | Tab で全操作に届き、フォーカスリングが見えること |

## 5. アクセシビリティ

- **ホバーでしか現れない部品を作らない**。`opacity-0 group-hover:opacity-100` で隠すボタンには `group-focus-within:opacity-100` と `focus-visible:opacity-100` を付け、タッチ端末（`@media (hover: none)`）では常に見せる。 メッセージの操作ボタン（コピー・読み上げ・編集して再送信）は `components/chat/message-action-button.tsx` の `MessageActionButton` を使う（これらを満たし、ラベルのツールチップも付く）。
- **押せる領域は 24×24px 以上**（WCAG 2.5.8）。主な利用端末は PC なので 44×44px までは求めないが、声で話す機能のようにスマホでも使われうる部品は 44×44px を目安にする。見た目のアイコンが小さくても、ボタンの領域で確保する。
- **色だけで区別しない**。状態は色とアイコン・テキストを組み合わせる。
- **フォーカスリングを消さない**。`outline-none` を書くなら代わりの `focus-visible:` の見た目を付ける。
- 画像には `alt`、アイコンだけのボタンには `aria-label`、装飾のアイコンには `aria-hidden`。

## 6. 動き

- **動きは状態の変化を説明するときだけ使う**。開く・閉じる・現れる・進行中を伝える。注目を集めるための装飾の動きは使わない。
- 長さの目安: 小さな部品（ホバー・ツールチップ）は 150ms、パネルの開閉・進捗バーの伸びは 200〜300ms。300ms を超えない。回り続ける表示（入力中の点・`Spinner`）は進行中を伝えるためなので対象外。
- **`prefers-reduced-motion` を尊重する**。`globals.css` の全体のルールが、設定が有効なときにすべてのトランジションとアニメーションをほぼ即時にする。回転する読み込み表示（`Spinner`）は `motion-safe:` で止まるので、進行中であることは別の手段（`aria-label` の `role="status"`）でも伝える。
- 読み込みの動きは、0.3〜0.5 秒より速く終わる処理では出さない（ちらつくため）。

## 7. AI の応答の見せ方

- 送信したら、応答の最初の文字が届く前に、すぐ待ち状態を見せる。最初の文字が届いたら待ち状態を消して本文に置き換える。
- 本文はストリーミングで出す。ストリーミング中の見た目の崩れ（未閉じのコードフェンスなど）は既存の `closeOpenCodeFence()` のように補う。
- 失敗したら、どこまで届いたかを残し、再試行の手段を出す。
- AI の内部の判断（事前分析・観点の地図の中身）は、学習者の思考を先回りしない範囲でだけ見せる。

---

## 8. やらないこと

- 半透明・ガラスの質感の操作部品（背景によって読めなくなる）
- 意味の無いグラデーション・影・色付きのアイコン背景
- ホバーしないと存在に気づけない操作
- 1 画面に強調色の塗りを何か所も置くこと
- 画面ごとに違う位置・違う文言の同じ操作
- 既存製品の見た目を写すこと（機能の言葉で設計する）
