# ADR-015: 文字起こしの精度は、セッションの用語を keywords で渡して上げる

## Status

Accepted（2026-10-13。実装は #493）

## Context

声で話す・入力欄のマイクの文字起こし（`gpt-transcribe`）で、専門用語・英字の略語が誤ることがある（ADR-007 で「用語ヒント（`keywords`）は後続で導入」としていた）。誤った用語は事前分析と観点の到達の判定に入る。

実データ（`dialogue_messages.raw_transcript`）は 2026-10-13 の時点で 14 件しかなく、傾向を集計できなかった。そこで、誤りやすい語を含む 30 文（5 トピック × 専門用語・同音異義の漢字・固有名詞・英語の略語・数字・言いよどみ）を 1 人が読み上げて録音した音声セットを作り、案ごとに 3 回ずつ文字起こしして比べた（`server/evals/transcription.py`。音声はリポジトリに入れない）。指標は、各文の確かめる用語が正しい表記で出た割合（用語の正解率）を主にし、文字誤り率（CER）・ヒントに入れたが話していない語が出た数・遅延・費用を見た。

| 案 | 用語の正解率 | CER | 遅延 p50 | 費用 |
| --- | --- | --- | --- | --- |
| 今の声で話す（定型文 + トピックの prompt） | 93.0% | 5.0% | 1.3 秒 | 基準 |
| 今の入力欄のマイク（prompt なし） | 90.7% | 6.6% | 0.9 秒 | 基準 |
| prompt に観点名と直前の質問を足す | 95.7% | 4.8% | 変わらない | 変わらない |
| prompt に直前の発言を足す | 93.0% | 4.9% | 変わらない | 変わらない |
| keywords に用語の一覧（手で作成）を渡す | 100% | 3.5% | 変わらない | 変わらない |
| 文字起こしの後に LLM で補正する | 98.4% | 4.0% | 2.6 秒 | LLM の分が増える |
| モデルを `gpt-4o-transcribe` に替える | 95.3% | 3.5% | 変わらない | +33% |
| モデルを `gpt-4o-mini-transcribe` に替える | 90.7% | 5.2% | 変わらない | −33% |

採用した方法（LLM がセッションの始めに作る一覧）で測り直した結果:

| 案 | 用語の正解率 | CER |
| --- | --- | --- |
| 声で話す + 生成した keywords | 95.0% | 4.7% |
| 入力欄のマイク + トピックの prompt + 生成した keywords | 95.3% | 4.6% |

どの案でも、ヒントに入れたが話していない語が出た誤りは 0 件だった。

## Decision

- **文字起こしの API に、セッションの用語の一覧を `keywords` で渡す**。声で話すと入力欄のマイクの両方に入れる
- 一覧は「トピック名 + 観点名 + LLM が挙げた用語（10〜20 件）」。LLM は学習では深さの地図ができた後、復習では開始時に 1 回だけ呼び（`generate-transcription-keywords`）、出どころ（トピック・観点・補足）が変わったときだけ作り直す。グラフの外で、応答の後にバックグラウンドで作り、`dialogue_sessions.transcription_keywords` に保存する。作るまでの間（聞き取りの途中など）はトピック名だけを渡す
- 入力欄のマイクにも、prompt でトピック名を渡す（「以上」の定型文は声で話すだけ）

## Reasons

- **keywords**: 遅延も費用も増えずに、用語の誤りが最も減った。prompt に文脈を足す案は、「WAL」を 3 回とも「ログ」に置き換えるなど、話した語を言い換える誤りを生んだ。keywords だけの案ではこれが起きなかった
- **LLM で一覧を作る**: 測定で効いた語（「輻輳制御」「SYN」など）は観点名には入っておらず、トピックと観点名だけでは届かない。会話から機械的に英字・カタカナを拾う方法では、AI がまだ口にしていない語や漢字の用語が入らない。1 セッション 1 回なら費用は小さい
- **グラフの外で作る**: プロンプトに注入しない値なので、state と eval の再現に要らない（ADR-007 の `raw_transcript` と同じ扱い）。応答を待たせず、既存のプロンプトの fingerprint も動かさない
- **採らない案**
  - 文字起こしの後の LLM 補正: 遅延が約 2 倍になるのに、keywords に届かない。声で話すは最後の区間の文字起こしを待って送るので、遅延がそのまま会話の間になる
  - モデルの変更: `gpt-4o-transcribe` は費用が 33% 増えて、用語の正解率は keywords に届かない。`gpt-4o-mini-transcribe` は今より悪い
  - 直前の発言・質問を prompt に足す: 改善が小さく、言い換えの誤りが出る
  - 訂正から学ぶ: 直した記録が無く測れない。仕組みは「keywords に何を入れるか」の一つなので、記録が溜まってから keywords の上に足せる（別の Issue）

## Consequences

- 生成した一覧では、手で作った一覧（100%）に届かない（声で話すは 95.0%）。学習者が口にする語を前もって当て切れないため（「fork」「輻輳制御」「O(log n)」が一覧に入らなかった）。会話に出た用語の追加と、訂正から学ぶ方法は別の Issue で検討する
- 一覧に入っていても外す語がある（「WAL」）。一覧が長いほど 1 語の効き目が薄まる可能性があるが、30 文では確かめられていない
- 測定は話者 1 人・30 文で、3 回の出力はほぼ同じだった（実質 30 サンプル）。差の小さい案どうしの順位は入れ替わりうる
- 用語に引っ張られて別の語に化けることがある（「障害の後」→「障害ノート」）。一覧はセッションに関係する語に絞る
- `dialogue_sessions` に一覧を保存する。文字起こしの内容ではなく、トピックから作った語なので、ADR-012 の個人データの範囲は広がらない
- prompt の定型文の冒頭（「話し終えたら」）が、そのまま文字起こしとして送られた実例が 1 件ある（無音に近い区間で prompt が出た可能性）。keywords でも、話していない語が出ないかを実データで見続ける
