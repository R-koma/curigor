# ADR-007: 音声対話はカスケード型で段階導入し、フェーズ1はサーバー経由の STT（音声入力）のみとする

## Status

Accepted（2026-10-02。実装は #41。フェーズ2は ADR-008 で更新）

## ADR-008 との違い

この ADR は音声対話の**方式**（カスケード型・STT から段階導入）と、**フェーズ1の音声入力**（確認・修正してから送る）を決める。自動送信と応答の読み上げは、ここでは決めておらず、フェーズ2として別の ADR で決める（ADR-008）。

| | 音声入力（ADR-007 / #41） | 音声モード（ADR-008 / #378） |
| --- | --- | --- |
| 何を決めたか | 音声対話の**方式**（カスケード型・段階導入）と、フェーズ1の音声入力 | 音声入力の**上に足す別モード**（自動送信・読み上げ）と、その例外 |
| 位置づけ | 常に使える入力補助。マイクを押すと文字が入力欄に入る | ユーザーがトグルで切り替える。オフなら音声入力のまま |
| 送信 | 入力欄で確認・修正してから、手動で送る（D4: 自動送信しない） | 録音を止めたら自動で送る。**聞き取りカードの表示中だけ**入力欄で確認して手動で送る |
| 応答 | 文字のみ | 文字に加えて読み上げる（`POST /api/speech`） |
| 誤認識の直し方 | 送信**前**に入力欄で直す | 送信**後**に鉛筆ボタンで入力欄へ戻して直す（カードでは送信前） |
| 録音の開始 | ユーザー操作 | ユーザー操作（読み上げ後の自動録音はしない） |
| `input_mode` | `voice` | `voice_auto`（自動送信した発言。取り消して直して送り直した発言も含む）。最初から入力欄で確認して送った発言は `voice` |
| 実装 | #379〜#385 | #378 |

## Context

音声チャット機能（#41）を導入するにあたり、方式を選ぶ必要があった。候補は次の 3 つ。

1. **STT のみ**：音声を文字起こしし、既存のテキスト対話に流す
2. **カスケード型の双方向**：STT → 既存の LangGraph（テキスト）→ TTS
3. **speech-to-speech 型**：Realtime API などで、音声を入れると 1 つのモデルが音声で直接返す

前提は次のとおり。

- 本アプリは「プロテジェ効果」が中核で、**ユーザーが説明する側**になる。AI の発話は短い問い返しが中心で、ユーザーの発話は長い説明になる
- 利用想定は**机での学習**で、ハンズフリーは要件ではない
- 対話の品質は LangGraph 側の仕組みで管理している。`prepare_turn` / `respond` の分割、深さの地図に沿った応答、`covered_aspects` から決める区切りの提案、eval の regression（`prompt_fingerprint` / `--replay-mode pinned`）、Langfuse の 1 ターン = 1 trace がそれにあたる

## Decision

**音声対話はカスケード型で段階的に導入する。speech-to-speech 型は採用しない。**

| フェーズ | 内容 | 状態 |
|---|---|---|
| 1 | 音声入力（push-to-talk・録音停止後に一括で文字起こし・送信前に確認と修正） | #41 で実装 |
| 2 | 応答の読み上げ（TTS）を任意でオンにする | 音声モードの一部として #378 で実装（ADR-008） |
| 3 | ハンズフリー化（読み上げ後の自動録音・無音検出による自動停止・割り込み） | 未実装。遅延が UX の問題になるとデータで分かってから検討 |

フェーズ1の主な決定は次のとおり。詳細と制限値は #41 の決定事項を正本とする。

- 文字起こしは**サーバー経由の API**（`gpt-transcribe`）で行う。ブラウザの Web Speech API は使わない
- 送信経路は **REST**（`POST /api/transcriptions`）にし、WebSocket には載せない
- 文字起こし結果は入力欄に入れ、**ユーザーが確認・修正してから**、既存の `user_message` として送る
- **音声ファイルは保存しない**
- `dialogue_messages` に `input_mode` と `raw_transcript`（修正前の文字起こし）を残す。**state には載せない**

## Reasons

- **speech-to-speech 型を採用しない**: 応答を生成するのが Realtime 側のモデルになり、Context に挙げた品質管理の仕組みがどれも成り立たなくなる。tool calling で LangGraph を呼ぶ構成にしても、対話の主導権は Realtime 側に残る。費用も高くなる（下記「費用の比較」）。ただし `gpt-realtime-mini` なら差は 2 倍弱まで縮むので、採用しない主な理由は費用ではなく品質管理である
- **カスケード型・STT から始める**: 音声の価値は入力側に偏っており、説明の長いユーザーにとってタイピングの負担を減らす効果が最も大きい。STT はグラフにテキストを渡すだけなので、グラフ・state・eval・capture を変えずに済む。フェーズ2の TTS も、既存のトークンストリームの上に足すだけで済み、作り直しにならない
- **送信前に確認させる**: 学習対象の専門用語は誤認識されやすい。誤認識をそのまま送ると、事前分析と `covered_aspects` に誤りが入り込む。机での利用なら、確認のひと手間は UX を損なわない
- **サーバー経由の API**: Web Speech API は精度とブラウザ対応にばらつきがある。また、モデルの選択、用語ヒント（`keywords`。後続で導入）、使用量の上限をアプリ側で制御できない
- **REST**: 文字起こしは送信前の入力補助で、ターンの一部ではない。WS に載せると `_handle_user_message` のメッセージ順序管理や、応答が返らなかったターンのロールバックと絡む。REST なら、失敗してもチャットの状態は変わらない
- **音声を保存しない**: プライバシー面の負担と、ストレージ（#128）の容量を避ける。誤認識の分析に必要な情報は `raw_transcript` で足りる
- **`raw_transcript` を state に入れない**: プロンプトに注入しない値なので、ターンの再現に要らない（CLAUDE.md の「プロンプトを変える決定値は state に残す」の対象外）

### 費用の比較（2026-10 時点）

単価は [OpenAI Pricing](https://developers.openai.com/api/docs/pricing) と [gpt-realtime](https://developers.openai.com/api/docs/models/gpt-realtime)、音声のトークン換算は [Realtime API の課金](https://developers.openai.com/api/docs/guides/realtime-costs)（ユーザー音声は 100ms で 1 トークン = 600 トークン/分、モデル音声は 50ms で 1 トークン = 1,200 トークン/分）による。

| 方式 | ユーザーの音声 | モデルの音声 |
|---|---|---|
| カスケード型 | STT `gpt-transcribe` $0.0045/分 | TTS `gpt-4o-mini-tts` 約 $0.015/分（※） |
| `gpt-realtime`（音声 入力 $32・出力 $64 / 1M トークン） | $0.0192/分 | $0.0768/分 |
| `gpt-realtime-mini`（音声 入力 $10・出力 $20 / 1M トークン） | $0.006/分 | $0.024/分 |

※ `gpt-4o-mini-tts` の公式の単価は音声出力 $12 / 1M トークンで、分あたりの値は公式に載っていない。約 $0.015/分は一般に引用される推定値で、フェーズ2の実装（#378）の運用後に `speech_usages` の文字数と OpenAI の使用量から実測して確かめる。

Realtime API は応答のたびに会話全体を入力として再送し、その分も課金される。キャッシュが効けば $0.40（mini は $0.30）/ 1M トークンまで下がるが、会話の内容を変えるとキャッシュが外れる。

30 分のセッションで、ユーザーが 15 分・モデルが 5 分話し、15 往復すると仮定した場合の音声部分の費用は次のとおり。再送される文脈は 1 往復あたり平均約 7,500 トークンで、合計約 11 万トークンになる。

| 方式 | 1 セッションの費用 | カスケード型との比 |
|---|---|---|
| カスケード型（STT + TTS） | 約 $0.14（フェーズ1の STT だけなら約 $0.07） | — |
| `gpt-realtime` | 約 $0.72（文脈がすべてキャッシュされた場合）〜 約 $4.3（キャッシュなし） | 約 5〜30 倍 |
| `gpt-realtime-mini` | 約 $0.24 〜 約 $1.3 | 約 1.7〜9 倍 |

カスケード型には、このほかに既存の対話 LLM（`gpt-6-luna`）の費用がかかる。Realtime API ではこれが不要になるが、テキストの単価なので音声部分に比べて小さい。

## Consequences

- フェーズ1では LangGraph・`LearningState`・eval・capture に変更が入らない。`GRAPH_VERSION` も上げない
- 音声入力の発言は、グラフからはテキスト入力と区別できない。音声入力の影響（誤認識の頻度、説明の長さ）は `dialogue_messages` の `input_mode` / `raw_transcript` から分析する
- 文字起こしはグラフの外で行うため、Langfuse には別の trace（`transcribe-audio`）として記録する。`traced_graph_run` の外で metadata を扱う際に、session のグルーピングを壊さないよう注意が要る
- 文字起こしの使用量を数えるため、音声は保存しなくても `transcription_usages` テーブルが要る
- カスケード型を選んだことで、フェーズ2以降の応答遅延は「STT + 事前分析 + 応答の最初のトークン + TTS」の合計になる。特に事前分析の LLM 呼び出しが 1 回分の遅延を加える。会話の自然さが問題になった場合も、まずカスケード内の改善（文単位の TTS ストリーミングなど）で対処し、speech-to-speech 型への移行はこの ADR を改めて見直す判断として扱う
