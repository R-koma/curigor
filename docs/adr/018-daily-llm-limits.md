# ADR-018: LLM を呼ぶ操作の 1 日の上限を、アプリの Postgres で回数として数える

## Status

Accepted（2026-10-26。実装は #777。入口の制限など残りは #496）

## Context

友人に無料でベータを使ってもらう間、1 人が使える LLM の費用に上限が要る。文字起こし・読み上げ・整形には 1 日の上限があるが（#773）、セッションの開始・発言・まとめの作成には無く、1 人がいくらでも LLM を呼べた。

入口（WAF・ロードバランサー）の IP 単位のレート制限は #496 で扱うが、デプロイ先が決まる #128 の後になる。それまでアプリの中で費用を頭打ちにする。

## Decision

1. **数える場所**: `llm_usages`（`user_id`・`operation`・`created_at`）に 1 回を 1 行で記録し、暦日（`REVIEW_TIMEZONE`）ごとに数える。判定と記録は 1 つのトランザクションの中で、`pg_advisory_xact_lock(hashtext('llm_usages:' || operation || ':' || user_id))` を取ってから行う（`repositories/llm_usage_repository.py`）。台数が増えても、同時のリクエストがそろって上限を抜けない。予約の考え方は #773 と同じ
2. **数える操作**: セッションの開始（`session_start`。学習・インプット・まとめ・復習の `start_*`）、発言（`turn`）、まとめの下書きの作成（`synthesis`）。数えない操作は、再開（`resume_session`）、セッションの終了（ノート・フィードバックの生成）、発言の取り消し、ノートの編集（トピック・要約・本文を変える `PATCH /api/notes/{id}`）による埋め込みの生成（本文のハッシュが同じなら API を呼ばない）。ノートの編集による復習の質問プランの作り直しは、本文（と復習での追記）のハッシュとプロンプトの版が手元のプランと同じなら作り直さず、作り直すときだけ `review_plan` として数える（2026-10-27 に追加）
3. **上限の値**: 開始 30 回・発言 150 回・まとめ 10 回・編集による質問プランの作り直し 30 回（`core/config.py` の定数。環境変数にしない）。質問プランの作り直しは編集の後に裏で走るので、上限を超えたら利用者には知らせずに作り直しを飛ばす（編集は保存され、復習は手元のプランで始まる）
4. **記録は LLM を呼ぶ前に行う**。上限のときは LLM を呼ばず、DB にも state にも何も足さない。WebSocket は `daily_session_limit_reached`・`daily_turn_limit_reached` の `error`、REST は 429 `daily_synthesis_limit_reached`
5. **記録を消すのは、LLM を呼ばずに終わったと確かに言える場合だけ**:
   - 開始: 開始のハンドラが `None` を返した（ノート・まとめノート・改善の対象が無い、まとめの対象のつながりが無い、など別の理由で拒否した）
   - 発言: `client_message_id` が重複していた
   - まとめ: LLM を呼ぶ前の失敗（事前確認の `CollectionNotFoundError`・`NoteCountError`）
6. **記録を残す場合**: 開始のハンドラの途中で例外になった、発言が `turn_failed`・停止・引き継ぎになった、まとめが `SynthesisGenerationError` や `CollectionDeletedDuringSynthesisError`（LLM の後の外部キー違反）で失敗した。切断・停止も消さない

## Reasons

- **台帳を Postgres に置く理由**: 追加のインフラが要らず、複数台でも 1 つの数になる。入口の制限が入るまでの、費用の頭打ちとしては足りる
- **上限の値の根拠**: ローカルの開発者アカウントの 22 日の実績は、1 日あたり発言が最大 37・p90 28、セッションが最大 9・p90 5、ノートの生成が最大 5。通常の使い方の 3〜5 倍で、普通に使う人には当たらず、暴走や悪用だけを止める。ノートの生成は 1 セッションに 1 回なので、開始の上限で頭打ちになる
- **失敗でも消さない理由**: 上流が課金したかを、サーバーは確かめられない。特に WebSocket は、ストリームの途中でクライアントがソケットを閉じると送信が例外になり、失敗の経路に入る。失敗を返金すると、クライアントが自分で失敗を起こして上限を抜けられる。まとめも、LLM の生成中にまとめノートを削除すると外部キー違反を起こせるので同じ。正直な失敗で 1 回失う費用より、抜け道を塞ぐことを選んだ
- **LLM を呼ぶ前の拒否は消す理由**: 何も課金されておらず、利用者の側に原因が無いので、回数を失わせない

## Consequences

- LLM を呼ぶ新しい入口（WebSocket のメッセージ・REST のルート）を足すときは、数えるかを決める。数えるなら `LlmOperation` に値を足し、`llm_usages.operation` の CHECK 制約も変える
- 文字起こし・読み上げ・整形の 3 つの上限は今のテーブルと単位（秒・文字数）のまま。`llm_usages` への載せ替えは #496
- ノートの編集による埋め込みと、セッションの終了は数えない。学習・復習の終了による質問プランの作り直しも数えない（開始の上限で頭打ちになる）
- 料金プランやお試しによる上限の違い、管理者・内部のテストの扱い、上限に近づいたときの予告は #496
- 開始の拒否、重複の発言、事前確認の失敗だけが回数を返す。サーバーの失敗で回数が減ったと問い合わせが来ても、仕様どおり
