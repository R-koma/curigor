# LangGraph ワークフロー（`server/graph/`・WebSocket）

ルートの `CLAUDE.md` から分けた規約。一致するファイルを Read / Edit すると自動で読み込まれる。グラフのノード・state・プロンプト・`ws/chat`を触る前に関係すると分かっているときは先に読む。

## ノードと state の規則

- 入口の分岐は `graph/builder.py` の `route_entry`、ループを抜けるかは経路ごとの `route_after_learning_dialogue` / `route_after_review_dialogue` / `route_after_synthesis_dialogue` / `route_after_explore_dialogue` が `should_generate_note` で決める
- 復習セッション: `review_start` / `review_dialogue` が既存ノートの本文・要約と前回の改善点（`prior_improvements`）をプロンプト（`graph/prompts/review.py`）に注入し、`update_note_and_feedback` でノート・フィードバック・復習スケジュールを更新する（`generate_note` / `generate_feedback` は通らない）。`review_dialogue` は毎ターン事前分析（`ReviewTurnAnalysis.wants_to_end_session`）で終える意志を判定する。`should_generate_note` は立てない（終了は下の「会話でのセッション終了」）
- **synthesis セッションは、いま何番目のつながりを聞いているかを state に持たず、`messages` のユーザー発言の数から決める**（`graph/nodes/synthesis.py` の `current_connection_index`）。発言の取り消しと応答の無い発言の巻き戻しは `messages` だけを巻き戻すので、位置を別の値で持つとずれる。synthesis セッションは再開しない（`find_resumable_by_user` の対象外）
- `interrupt_before=["learning_dialogue", "review_dialogue", "synthesis_dialogue", "explore_dialogue"]` でユーザー入力待ちのため毎ターン中断する（再開はチェックポイントから）
- ノードスパン・LLM 生成の計測は Langfuse が自動で行う（`observability/langfuse_tracing.py`）。詳細は `.claude/rules/server/langfuse.md`
- グラフ状態は `langgraph-checkpoint-postgres` で DB に永続化
- `LearningState` は `session_type`（`"learning"` / `"review"` / `"synthesis"` / `"explore"`）で分岐
- **プロンプトを変える決定値は state に残す**。`learning_dialogue` の事前分析が決める `response_mode` / `selected_aspect`（`turn_analysis`）は、無いと会話履歴と state からターンを再現できず eval の regression が成立しない。同じ理由で、新しく「プロンプトに注入するがどこにも保存しない値」を作らないこと
- **区切りの提案（`wrap_up`）は LLM ではなく `covered_aspects` から決定的に決める**（`graph/coverage.py` の `coverage_progress`）。exemplified 以上の観点が `WRAP_UP_MIN_ASPECTS` 個（`focus_aspects` 指定時はその全観点）に届き、誤りが無く、未提案（`wrap_up_offered`）のターンだけ質問をやめて区切りを提案する。提案は 1 セッション 1 回で、終了はさせない。`focus_aspects` は判定上 `covered_aspects` と**表記の完全一致**で照合するため、事前分析が表記を揺らすと完了しない。取り消し・セッションの引き継ぎ・停止はどれも、発言の直前のチェックポイント（`aget_state_history` でメッセージの並びが取り消し後と一致する最新のもの）の値で `messages` 以外のキーをすべて戻す（`_rewind_update`。そのチェックポイントに無かったキーは `None` を書く（`StateSnapshot.values` は値を持ったことのないキーを含まないため）。戻さないと、取り消した答えで進んだ点や観点に対して再送の答えが判定される）。取り消しと停止は加えて `end_confirmation`・`pending_topic_correction` を `None` にする（`_cancelled_turn_update`）。チェックポイントが見つからないときだけ、`messages` と `turn_count` を戻す
- **毎ターン置き換わる state フィールドは、値が無いターンにも明示的に `None` を書く**。LangGraph はキーを省いた更新では前ターンの値を保持するため、書かないとチェックポイント履歴を辿る側（eval エクスポート）が別ターンの値を読む。累積する `covered_aspects` と、置き換わる `turn_analysis` の違いに注意
- state フィールドの追加は `NotRequired` にし、読む側は `.get()` で欠損許容する（旧チェックポイントにキーが無い）。トポロジーが変わらないなら `GRAPH_VERSION` は上げない。入口の経路（新しい `session_type` の分岐とノード）を足すだけでも上げなくてよく、`tests/unit/test_graph_topology_compat.py` が固定する。このテストは無条件の自己ループを持つ簡易グラフなので、入口の経路の追加で既存スレッドが再開できることだけを固定し、実際の条件付きエッジは検証しない。上げると進行中セッションが全て再開不可になる。ただしフィールドの削除・改名は例外（「注意事項」節参照）。インプットを疑問起点に変えて使わなくなった `explore_overview`・`explained_aspects`・`explore_setup_failed` は、初版が本番に出た後だったので、上げる代わりに `LearningState` に宣言だけ残している（値を持つ進行中のスレッドが中断し続けないため。`tests/unit/test_graph_topology_compat.py` が固定する）
- **`learning_dialogue` は `intake_complete` キーの「有無」で3経路に振り分けるルーター**: キー欠損 = デプロイ前に始まった旧セッション（旧経路 `prepare_turn`/`respond` をそのまま実行）、`False` = 聞き取り中（`graph/nodes/_intake.py`）、`True` + `depth_map` あり = 地図駆動（`_map_dialogue.py`）、`True` + `depth_map` なし = 地図生成に失敗した旧経路フォールバック。値ではなく**有無**で旧セッションを見分けるため、`learning_start` は新規セッションで必ず `intake_complete=False` を書く（省くと新規セッションが旧経路へ落ちる）。`evals/eval.py` の regression が旧 capture を再生できるのも、`to_state`（`evals/replay.py`）がこのキーを持たないから。聞き取り中（`intake_complete=False`）は進捗（`LearningProgress`）を送らない（地図が無く、旧経路のフォールバックが意味のない 0/3 を返すため）。聞き取りの完了ターンで地図生成が失敗すると `handle_intake_turn` は `messages` キーを含まない dict を返し、ルーターが旧経路で応答を作る（`_intake.py` から `learning_dialogue.py` を import すると循環になるため）。`evals/tools/capture.py` は `intake_complete` を持つセッションを `meta.route: "map"` のレコードとして capture する（対象は order 6 以降の、直前の state に `depth_map` があるターンだけ。声かけと、地図生成に失敗して旧経路で応答したターンは対象外）。regression は地図のレコードを、`to_state` が `intake_complete=True` と生成直前の地図（`depth_map` / `map_covered` / `intake_message_count`）を入れて地図の経路で再生する（`pinned` は `turn_decision` から `MapTurnPlan` を組んで `respond_map` を直接呼ぶ）。`route` を持たない旧 capture には `intake_complete` を入れない
- **地図駆動の経路は、発言の種類（`user_intent`）を事前分析が毎ターン判定する**（`MapDialogueTurnAnalysis.user_intent`）。値は `explanation` / `dont_know` / `partial_dont_know` / `question` / `exhausted` / `end_session` で、応答のプロンプトはこれで分岐する（`map_question.py` の `_build_intent_section`）。キーワード判定（`classify_user_intent`）は、事前分析が失敗したときと、`user_intent` を持たない旧 capture の再生にだけ使う。「わからない」の連続回数 `unknown_streak` は LLM に決めさせず、直前の `turn_analysis`（`user_intent` と `unknown_streak`）から数える。直前の `turn_analysis` が空（意図の判定を入れる前の地図の経路が「わからない」のターンに残した値。旧 capture と、デプロイ前に始まったセッション）なら、それまでのユーザー発言をキーワード判定で遡って数える。`turn_analysis` には、既定値（`explanation`・0）のときはこの 2 つのキーを書かない（旧 capture の `turn_decision` と形をそろえ、pinned の再生で決定が一致するようにするため）。読む側は `.get` で既定値を補う。`end_session` の応答は問いを出さず、画面の「ノートを作成」へ案内するだけで、セッションは終えない（終了の確定は下の「会話でのセッション終了は確認を挟む」）。Langfuse の metadata の `intent` は、地図駆動では `user_intent` の値になる
- **`learning_start` は最初の発言から正規化したトピックと聞き取りカードを返す**: 発言は `state["topic"]` に入って `start_learning.topic` として届き、`learning_start` が短いトピック名へ正規化して `topic` を上書きする（`dialogue_sessions.topic` にも保存。NULL なら最初のユーザー発言）。カードは AIMessage の `additional_kwargs["intake_card"]`、回答は HumanMessage の `additional_kwargs["intake_answers"]` に載る。カードの回答は `dialogue_messages.intake_answers` にも保存し、画面はこれを印に吹き出しの代わりに 1 行の表示を出す（カード直後の自由文と再開時に見分けるため。`content` は LLM が読むので整形済みの本文のまま変えない）。ストリームは流れないので WS は `intake_question` で送り、`dialogue_messages.intake_card` に保存して再開時に復元する。聞き取りは1往復で必ず完了し、カードを無視した自由文の返信は従来どおり `extract_intake` で抽出する
- **最初の発言が曖昧なら、聞き取りカードの先頭に `topic` の質問を足す**: `IntakeCardDraft.topic_is_clear` が false（指示語だけ・対象が書かれていない）のとき、`build_intake_card` が候補（0〜3 件。手がかりが無ければ 0 件で、既定の選択肢は作らない）付きの質問を先頭に入れる。確かめたかどうかは state に持たず、カードの AIMessage に topic の質問があるかで決まる（`_intake.py` の `_topic_was_asked`）。それまでの `state["topic"]` は発言から作った仮の値で、聞き取りの完了ターンが回答（カードは `intake_answers.topic`、自由文は聞いたときだけ `extract_intake` が抽出する `topic`）で上書きしてから、深さの地図と声かけを作る。スキップされたら仮の値のまま。draft の生成に失敗したときは確かめない。`dialogue_sessions.topic` とナビバーは、各セッションが毎ターン `assistant_message_end.topic` で運ぶ値（学習は state のトピック、復習はノートのトピック、synthesis はまとめノート名）を `SessionContext.topic` と比べ、変わったときだけ更新する（聞き取りに限らない）。上限 60 字は `MAX_TOPIC_LENGTH`・`IntakeAnswers.topic`・クライアントの `TOPIC_MAX_LENGTH` で一致させる
- **地図駆動の対話の途中でトピックの訂正を受け付けるが、適用の前に必ず確認する**: 地図の事前分析（`MapDialogueTurnAnalysis.corrected_topic`）が訂正を判定すると、そのターンは適用せず、LLM を使わない確認文（`graph/topic_correction.py`）を AIMessage（`additional_kwargs["topic_correction_card"]`）で返し、`pending_topic_correction` を残す。ストリームは流れないので WS は `topic_correction_question` で送り、`dialogue_messages.topic_correction_card` に保存して再開時に復元する。回答は聞き取りカードと同じく通常の `user_message` に `topic_correction_answer`（`accept` / `decline`）を付けて送り、`dialogue_messages.topic_correction_answer` にも保存する。保留があり最後の発言に回答の印があるときだけ、事前分析と意図の判定を飛ばして決定的に分岐する。`accept` は聞き取りと同じ `generate_depth_map`（`graph/nodes/_depth_map_generation.py`）で地図を作り直し、学習の前提は引き継ぎ、`map_covered` を空に・`wrap_up_offered` を `False` に戻す（観点 id は地図ごとに振られ、旧トピックの到達度は対応しない）。訂正の発言の `observations` は捨てる。作り直しに失敗したら `topic` も地図も変えない（`failed`）。保留があるのに自由文を送ったら `decline` 扱いで保留を捨てる。今のトピックと（NFKC・大小無視で）同じなら訂正として扱わない。`pending_topic_correction` は毎ターン置き換わるので、`respond_map` は値が無いターンにも `None` を書く。判定は `turn_analysis.topic_correction`（`previous_topic` / `new_topic` / `status`: `asked` / `accepted` / `declined` / `failed`）に残る。`asked` のターンは LLM を呼ばないので、`turn_analysis` の `response_mode` などは空の値で埋めた名目の値で、プロンプトには注入されていない（`topic_correction.status` で見分ける）。`dialogue_sessions.topic` とナビバーは `assistant_message_end.topic` の既存経路で更新される。旧経路は対象外。回答の発言は取り消せない（`_handle_cancel_last_message` が拒否し、`_rollback_unanswered_turn` は聞き取りカードと同じく本文を空で返す）。確認を出したターンの取り消しは許し、`pending_topic_correction` も `None` に戻す
- **ヘッダーのトピック名からも編集できる**（`NavbarTopic` の `onEdit`）: クライアントの `AlertDialog` で確認済みなので、サーバーは確認を挟まずに適用する。`user_message.topic_edit` を付けた発言（本文は `topic_edit_text`。`dialogue_messages.topic_edit` にも保存）を 1 ターン流し、`prepare_map_turn` が事前分析を飛ばして会話での訂正の確定と同じ `generate_depth_map` で作り直す（保留中の `pending_topic_correction` は捨てる）。記録は `topic_correction` に `source: "header"` を足して残し（会話での訂正は `source` を書かない。読む側は `.get`）、応答のプロンプトは `accepted` / `failed` の節をそのまま使うので `MAP_PROMPT_FINGERPRINT` は動かない。WS は学習以外のセッション・聞き取りの途中・地図が無い・同じトピックでは発言ごと拒否して `topic_edit_rejected` を返す（DB にも state にも入れない）。この発言は取り消せず（`_handle_cancel_last_message` が拒否）、巻き戻しは本文を空で返す。eval の `full` 再生はトピック訂正への回答と同じく止まる
- **お試しの学習（`start_learning.trial`）は聞き取りを飛ばし、プロンプトを変えずに state だけで短くする**: `learning_start` が既定の目的（`graph/trial.py` の `TRIAL_PURPOSE`）で深さの地図を作り、中核観点を `TRIAL_CORE_ASPECTS`（1）件に絞り（残りは中核でない観点に落とす）、LLM を使わない声かけ（`additional_kwargs["trial_kickoff"]`）を返して `intake_complete=True` から始める。区切りの提案は中核観点が揃った時点なので早く出る。ストリームは流れないので、`_stream_ai_response` が声かけを 1 つの `assistant_message_chunk` で送る。地図の生成に失敗したら通常の聞き取りカードに戻る（完了ターンで同じく中核を絞る）。`MAP_PROMPT_FINGERPRINT`・`INTAKE_PROMPT_FINGERPRINT` は動かない（テストが値を固定する）。お試しかは `dialogue_sessions.is_trial` と state の `trial` に残し、Langfuse は `trial` タグ（再開でも付ける）、capture は `meta.trial` を付けて地図の対話を order 4 から拾う。ノート・フィードバック・復習予定は通常と同じ。入口はダッシュボード（ノートが 0 件のときだけ `TrialLearningCard`）から `/learn?trial=<id>` で、トピックの候補はクライアントの `lib/trial.ts` が持つ。サーバーは回数を制限しない
- **学習メモからの学習（`start_learning.study_memo_id`）は聞き取りを飛ばす**: WS が学習メモを `user_id` で絞って読み（他のユーザーのもの・存在しないものは黙って無視して通常の聞き取りから始める）、トピック（クライアントが送ったものは使わない）・教材・地図（`memo_depth_map`）・用語の表記と読み（`memo_terms`。意味・疑問と回答は渡さない）を `initial_state` に入れる。`learning_start` はお試しと同じく LLM を使わない声かけ（`additional_kwargs["memo_kickoff"]`。ストリームは流れないので `_UNSTREAMED_TEXT_KEYS` に入れて 1 つのチャンクで送る）で `intake_complete=True` から始め、`map_covered` は空（教わったことは説明できたことではない）・目的と前提知識は空。関連する過去のノートは学習メモのトピックで 1 回だけ取る。学習メモがあるとき `trial` は付けない。`study_memo_id` は `dialogue_sessions` にも保存し（学習メモが消えたら NULL）、ダッシュボードの「引き継ぎ済み」の判定（`handed_over`。そのメモを持つ学習セッションが `completed` で `note_id` がある。ノートを作らずに終えたものは数えない）に使う。トピックの訂正を受け入れたら（チャットでも見出しの編集でも）学習メモの用語は state から外し、以降のターンのプロンプトにも入れない（学習メモのトピックを離れたため）。ただし `study_memo_id` は残り、セッションは学習メモに紐づいたままなので、終えれば引き継ぎ済みになる
- **応答のプロンプトの「先に教わった用語」の節は `memo_terms` があるときだけ**: 表記と読みだけを入れ、「未出の概念を持ち出さない」規則の例外にする（この節にある用語だけ）。意味や使い方は説明させない。ノートの節と同じく、無いときのプロンプトは変えない。節は `MAP_PROMPT_FINGERPRINT` に含まれるので、この節を足したことで値が動いた（`c8a87cb60d6e` → `8877a6584e85`）。既存の地図ベースライン（`map-v4-full.json`）は旧い値で取ったため、次の地図の regression は新しいベースラインを取り直してから比べる。その後、表記のルール（#611）を `QUESTION_PROMPT_BASE` に差し込んだので `8877a6584e85` → `46f81c2f62ba` に動いた。#502 で用語の導入（まだ口にしていない用語は名前と定義を先に述べず、知っていれば説明してもらう）と送信前の答えの先出しの確認を地図の経路に足したので `46f81c2f62ba` → `2ec014b2c769` に動き、学習者がまだ触れていない観点（`map_covered` に無い）では性質を問わず言葉を知っているかを問う規則を足して `2047bbe3aa76` に動いた。長い説明を段落・箇条書きで構造化する表記のルール（`CHAT_STRUCTURE_RULES`）を足して `dd1bafa56988` に動いた
- **関連する過去のノート（`related_notes`）は聞き取りの完了ターンで 1 回だけ取り、以後は変えない**: `handle_intake_turn` が確定したトピックと学習目的を埋め込み（`services/related_notes.py`。Langfuse は `embed-related-notes-query`）、同じユーザーのノートを近い順に `RELATED_NOTES_LIMIT` 件まで（`RELATED_NOTES_MIN_SIMILARITY` 以上）state に書く。該当が無いとき・埋め込みや検索に失敗したとき（`RELATED_NOTES_TIMEOUT_SECONDS` で打ち切る）も空リストを書く。深さの地図の生成（前提知識と同じ扱い）と地図駆動の応答（`map_question.py` の「過去に学んだノート」の節。未出の概念の規則の例外はこの節に書き、ノートが無いときのプロンプトは変えない）に注入する。トピックの訂正で地図を作り直すときも取り直さず同じ値を渡す。キーが無い state（この機能より前のセッション・旧 capture）は注入しない。capture は state にキーがあるときだけ `input.graph_state.related_notes` に入れ、regression はそれを再生する（既存の golden では効果を測れない）
- **`should_generate_note` は学習・復習の全対話ノード（`respond` / `respond_map` / 聞き取りの `base_updates` / `review_dialogue`）で常に `False` を返す**: セッションはユーザーの明示的な終了操作で完了し、終了スイッチは `api/websocket/chat.py` の `_handle_end_session` が外部から立てる。対話ノードから立てると、確認を挟む前に終わってしまう
- **会話でのセッション終了は確認を挟む**（#449）: 地図経路は `user_intent == "end_session"`、復習は `wants_to_end_session` で終える意志を判定し、ノードは `end_confirmation`（`offered` / `confirmed` / `None`。毎ターン置き換わるので値が無いターンも `None` を書く）を書く。区切りの提案（`wrap_up`）のターンも `offered`。`offered` の次のターンで再び終える意志が判定されると `confirmed` になり、ノードは LLM を呼ばず応答も足さない（アシスタントの行も保存されないので capture の対象にならない）。WS の `_handle_user_message` が `confirmed` を見て終了ボタンと同じ `_handle_end_session` を呼び、メインのループは終了後に抜ける（`end_session` と同じ）。旧経路は会話での終了を判定しない。取り消し（`_handle_cancel_last_message`）は `end_confirmation` を `None` に戻す。確認ボタンは `assistant_message_end.end_confirmation` / `session_resumed.end_confirmation`（`creates_note`）で送り、`_stream_ai_response` は学習・復習とも state を読んで載せる。表示の状態は保存せず、再開時に state から復元する
- **ノートを作るかは `graph/session_end.py` の `has_learner_content` だけで決める**: ボタン・会話・声のどれで終えても `_handle_end_session` が state を読んでこれを見て、偽ならノート・フィードバック・復習予定を作らず `status = 'completed'`（`note_id` は NULL）で終え、`session_ended.note_skipped` を送る。復習は `review_answered`（終える意志だけの発言は数えない）で判定し、このキーが無い（導入前に始まった）セッションは、`review_start` がトピックを最初の HumanMessage として入れるので、それを除いた HumanMessage の数で数える

- **インプットセッション（`explore`）は疑問起点で、教材カードも全体像も出さない**: `explore_start` が最初の発言にそのまま答える（2ターン目以降と同じ事前分析・応答。`_explore_dialogue.py` の `prepare_explore_turn` / `respond_explore` を共有）。トピックは1ターン目の事前分析が作り、無ければ発言を `MAX_TOPIC_LENGTH` で切る。開始のターンのトピックは `_start_session` がインプットだけ `dialogue_sessions.topic` に保存する（学習は聞き取りカードのトピックから保存するので経路が別）。発言の種類は `question` / `understood` / `material` / `end_session`。読み仮名は添えず、尋ねられたときだけ答える（用語集の読みも会話で示されたものだけ）。疑問への答えに理解を確かめる問いを添えない（問うのは「説明する」の役割）。`_UNSTREAMED_TEXT_KEYS` は `trial_kickoff` と `memo_kickoff` だけ（インプットに LLM を流さない文は無い）。インプットの発言は取り消しの拒否の対象外で、学習の聞き取り・トピック訂正と同じ規則だけが効く
- **用語は直前の AI の応答から事前分析で抜き出す**（応答の前に分析が走るため）。最後の応答の分は `generate_study_memo` が抜き出す。疑問は回答の AIMessage の `id` と組で積み、取り消しで消えた回答の疑問は学習メモに載せない。取り消しは `explore_terms` / `explore_questions` / `wrap_up_offered` も発言の直前の値に戻す（`_rewind_update`）
- **インプットセッションの区切りの提案は `understood` かつ `explore_questions` が1件以上・未提案（`wrap_up_offered`）のターンで1回だけ**（LLM ではなく事前分析の結果から決める。`prepare_explore_turn`）。終了の確認は学習・復習と同じ `end_confirmation` で、explore では `creates_note` が「学習メモを作る」の意味になる（`has_learner_content` の `explore` 分岐が用語・疑問のどちらかの有無で決める）。作った学習メモは `GET /api/dialogue-sessions/{id}/note-status` の `study_memo_id` で返し、`GET /api/study-memos` / `/api/study-memos/{id}` で読む（詳細に `depth_map` は載せない）
- **フィードバックの改善点から始めたインプットは `explore_gap` を持つ**: 最初のターンは事前分析を飛ばし、改善点の内容を説明する（改善点の文を `gap_question` で疑問の形にして学習メモに載せる）。`session_started` が `topic` / `first_message` を返すのはこの経路だけ
- **学習メモの地図は終了時に会話から作る**: `generate_study_memo` が `explore-teachback-map` で作り、失敗したら通常の `generate_depth_map`、それも無ければ観点の無い地図を保存する。学習メモの `overview` はこの地図の観点に、`organize-explore-memo` が振り分けた学習メモの疑問・用語の番号を足したもの（観点ごとの一行要約は作らない。古い行の `overview` には `summary` が残るが API は返さない）（番号は1つの観点にだけ入れ、`build_overview` が不正な番号を落とす）。全体の要約は `study_memos.summary`。整理に失敗したときと、観点が無い・回答済みの疑問も用語も無いときで整理を省いたときは、どちらも空。観点の無い地図の学習メモからの学習は、`_handle_start_learning` が `memo_depth_map` を入れず通常の聞き取りから始める（`memo_terms` などは入れる）
- **学習メモの編集（`PATCH /api/study-memos/{id}`）は疑問・用語を元の番号（`index`）つきで丸ごと受け取る**: 送られなかった番号は削除で、`services/study_memo_edit.py` が `overview` の `question_indices` / `term_indices` を新しい並びへ詰め直す（詰めないと削除の後ろの疑問・用語が別の観点に入る）。追加はできない。削除しても、そのメモから始めた学習セッションの `study_memo_id` が NULL になるだけでノートは残る。#731 より前の、要約も振り分けも無いメモは `scripts/backfill_study_memo_organization.py` で整理し直せる
- **学習メモは「教わった内容」でユーザーの理解ではない**: ノート・フィードバック・復習・埋め込み・関連ノートの検索にはつなげない

## 注意事項

- **聞き取りカードへの回答は取り消させない**: 取り消すと `intake_complete=True` のままカードが最後のメッセージに戻り、再回答が地図駆動の経路で処理される。`_handle_cancel_last_message` が `intake_answers` 付きの発言と、カード直後の自由文の返信の両方を拒否し、クライアントも鉛筆ボタンを出さない
- **LangGraph 永続化**: チェックポイントは DB に保存されるため、ローカル開発中にスキーマ変更するとチェックポイントとの不整合が起きる場合がある
- **ストリーミング対象ノード内の内部 LLM 呼び出しには `INTERNAL_LLM_TAG` を付ける**: WebSocket の `_stream_ai_response` は `stream_mode="messages"` を「ノード名が `_STREAMING_NODES` に含まれるか」だけでフィルタするため、対象ノード（例: `learning_dialogue`）の中で行う structured output 等の追加 LLM 呼び出しの出力（生 JSON）もそのままクライアントへ流れてしまう。内部呼び出しの runnable に `.with_config(tags=[INTERNAL_LLM_TAG])`（`graph/llm.py`）を付与すること。chat.py 側がこのタグ付きチャンクを除外する
- **`LearningState` のキー削除・改名は `GRAPH_VERSION` を上げる**（トポロジー不変でも例外）: `should_interrupt()`（`_algo.py`）はチェックポイントに永続化された `channel_versions` を丸ごと参照するが、`versions_seen[INTERRUPT]` の更新（`_loop.py`）は現在のグラフが宣言しているチャンネルにしか及ばない。宣言から消えたキーの version は永遠に「済」にならず、そのキーに値を持つ既存スレッドは `learning_dialogue` / `review_dialogue` の直前で毎ターン再中断し続け、進行不能になる
- **1 つのセッションを動かせるのは、最後に開始・再開した接続だけ**（#597）: `dialogue_sessions.connection_id` に接続ごとの ID を持ち、`_start_session` と `_handle_resume_session`（`claim_connection`。状態の確認と `in_progress` への更新も同じ UPDATE で行う）が書き換える。発言・取り消し・終了の前に `is_held_by`（持ち主かつ `in_progress`）で確かめ、外れていれば `session_taken_over` を送って閉じる（別のタブで新しいセッションを始めて `abandoned` になった・終了したセッションも同じ）。切断・異常終了の status の更新（`release_connection`）も持ち主のときだけ行い、引き継いだ側のセッションを `disconnect` / `failed` にしない。接続の間ずっとコネクションを借りる `pg_advisory_lock` は、プールを使い切るので使わない
- **応答の生成中に引き継がれたターンは無かったことにする**（#712）: 黙って切れた接続はサーバーが ping のタイムアウトまで気づかず生成を続けるので、同じタブの再接続でも起きる。`_handle_user_message` は `dialogue_sessions.turn_started_at`（生成中の印）を立て、生成の間 `TURN_OWNERSHIP_POLL_SECONDS` ごとに持ち主かを確かめ、外れたら生成を打ち切る。応答の保存は `finish_turn`（持ち主なら印を消す）と同じトランザクションで行い、`claim_connection` と行ロックで順序を決める。持ち主でなくなっていたら保存せず、`_undo_taken_over_turn` がそのターンで state に足したもの（発言より後のメッセージと、`messages` 以外のすべてのキーの発言の直前の値（`_rewind_update`）。値は `aupdate_state` が返したチェックポイントから読む）を戻して印を消す。発言は消さず、引き継いだ側の `_rollback_unanswered_turn` が `pending_message_rolled_back` で入力欄へ戻す。そのため再開は印が消えるまで待つ（`TURN_SETTLE_TIMEOUT_SECONDS` で諦めて印を消す。プロセスが落ちて印が残った場合のため。`TURN_STALE_AFTER` より古い印は待たない）。印は巻き戻しの後に消す（先に消すと、待っていた再開の巻き戻しと重なって 2 行消える）。開始のターン（`_start_session`）は対象外
- **応答の生成中も受信を続け、`cancel_last_message` で打ち切る**（`Inbox`）: `_stream_turn_while_held` は生成の task と `Inbox.receiving()` を並べて待つ。取り消せない発言（`_cancel_refusal`。生成中は返答の行がまだ無いので `message_order < 4` の判定はしない）への停止は `cancel_last_message_error` を返して生成を続ける。停止以外の文は `push_front` で戻し、返答の保存の後に順番どおり処理する。切断に気づいても生成は最後まで走らせて保存し、`WebSocketDisconnect` は次の `Inbox.next()` で送出する（後始末は今までどおり）。生成が終わった後に届いた停止は、完了後の取り消し（2 行消す）になる。生成が失敗して巻き戻した（`turn_failed`）時点で受け取り済みの停止は、`cancel_last_message_error` で断る（完了後の取り消しとして処理すると前のターンを消す）。打ち切ったら `_stop_turn` が巻き戻し（`_cancelled_turn_update`）→ 発言の行の削除 → `clear_turn` の順に行う（#712 と同じ理由）。停止の時点で持ち主でなくなっていたら、引き継がれたターンとして扱う
- **再開時に「応答が返らないまま残ったユーザーメッセージ」を巻き戻す**: 応答生成の途中で切断すると、DB と state にユーザーメッセージだけが残る。放置するとユーザーは同じ内容を再送するしかなく、履歴に同一発言が二重に残る（実セッションで発生）。`_handle_resume_session` の `_rollback_unanswered_turn()` が state（`RemoveMessage`）と DB の両方から取り除き、`pending_message_rolled_back` でクライアントの入力欄へ戻す。対話ノードは走っていないので `turn_count` は触らない。state への反映前に落ちた場合は DB 側にだけ残るので、そちらも同じ関数が拾う。聞き取りカードへの回答は整形済みの本文から構造化された回答を再現できないため、`pending_message_rolled_back` の `content` を空文字にする（カードが再び最後のメッセージになり、そこから答え直す）
- **対話ノードは `prepare_turn`（事前分析）と `respond`（応答生成）に分かれている**: eval が保存済みの決定を注入して応答生成だけ再実行できるようにするため（`--replay-mode pinned`）。分析の揺れとプロンプト改訂の効果を切り分けられなくなるので、この分割を戻さないこと。旧経路の `learning_dialogue` は両方を順に呼ぶだけ（地図駆動にも同じ `prepare_map_turn` / `respond_map` の分割がある）
- **地図の事前分析に渡す観点の一覧では、観点名に印を付けない**: LLM は観点を返すとき、一覧に見えた文字列を名前ごと写すので、名前に印があると `resolve_aspect` が一致させられず重複の観点が増える。中核かどうかは `_format_aspect_list` で名前と別の欄に書き、`resolve_aspect` も末尾の「（中核）」を除いて照合する。古いセッションと capture の地図には重複の観点（id `〇〇-中核`）が残っている
